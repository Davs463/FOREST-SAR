Fecha de referencia: noche del 14 de noviembre de 2026, Honduras. Deadline local conservador: domingo 15, 17:00 HN; confirmar con líder local. ## 1. Resultado y alcance
Desarrollar sobre el sitio existente una app navegable que muestre cambios candidatos de radar NISAR L2 GCOV en Distrito Central (Tegucigalpa/Comayagüela y La Tigra como área contextual), traduzca los datos y facilite verificar y colaborar. Coreografía: Find your partner → Tune the step → Spot the moves → Decide together. No es sistema de emergencia ni predicción agrícola. La investigación del equipo reporta fechas junio–octubre de 2026, pero no hay archivos de escenas ni catálogo validado en este paquete. Los IDs, cobertura, polarización y fechas se deben verificar al ejecutar.

P0: catálogo real y al menos una pareja compatible procesada reproduciblemente si los datos lo permiten; mapa/antes-después/capa de cambio, selector de área y fechas, indicadores, explicación y fuente; vista observaciones/ficha CSV; metodología; navegación responsive; demo pública sin login; build reproducible; QA. Si solo se consigue catálogo o una escena, publicar eso con estado explícito y comparación deshabilitada; no inventar una pareja. P1: comunidad local con posts/comentarios/votos, reportes, encuestas, directorio, biblioteca y PDF, eventos de prueba, UX pulida y modo bilingüe. P2: actualización automática desplegada, login real, backend, modelos, notificaciones, expansión global, recomendación de siembra, integraciones institucionales. P1 no debe impedir P0.

## 2. Reglas de arquitectura

**Obligatorio:** leer `docs/ARQUITECTURA_MODULAR.md` (v4.1). Define árbol, centralización de marca/config/rutas, diccionarios ES/EN, tokens CSS, interfaces entre módulos y aislamiento de errores. Sus criterios de aceptación complementan este plan; no justifican reescribir el stack. El motor científico lee configuración central y registra valores en snapshots.
1. Inspeccionar repositorio actual (package.json/lockfile, index, rutas, CSS, assets, Git, instrucciones locales). El sitio reciente del usuario no está adjunto en esta entrega; localhost de otra computadora no es accesible aquí. No suponer React, Vite ni backend; conservar lo existente. Si HTML/CSS/JS, mantenerlo. Si framework con build estático, usarlo y su lockfile. No migrar ni crear otro proyecto sin necesidad.
2. Python 3.11/3.12 local (venv) + earthaccess, numpy, rasterio, h5py, pytest, scipy opcional, harmony-py opcional, shapely si clipping real. Node según stack existente; Playwright para navegador. Leaflet si no hay mapa, Chart.js o SVG si no hay gráfico; respetar dependencias ya presentes. No Docker obligatorio ni microservicios. Las librerías de mapas no procesan radar.
3. Frontend estático consume JSON/GeoJSON y PNG/tiles georreferenciados; no entrega HDF5 grande al navegador. Usar GeoTIFF/COG para archivo científico y descarga si tamaño permite; no usar screenshot como entrada científica. Para Leaflet, exportar overlay de datos reproyectado a Web Mercator o tiles EPSG:3857 con transparencia y bounds calculados, o usar plugin raster compatible. Mantener raster numérico original; reproyección visual no se usa para hectáreas. Para un piloto pequeño, overlay PNG más bounds es suficiente. Atribuciones visibles y caché. No depender del API Earthdata al navegar.
4. Datos científicos versionados en `public/data` (o carpeta servida equivalente), datos crudos y credenciales fuera de dist y Git. Publicación transaccional: construir una carpeta de snapshot validada, luego actualizar manifest/puntero de forma atómica; preservar última válida. No reemplazar datos reales por fixtures. Solo el propietario sube dist a GoDaddy.
5. Comunidad con localStorage versionado, fixtures separadas; no base de datos en P0/P1. Visitor/volunteer/technician como roles de simulación, no control de acceso ni autenticación. Botón “Try demo role”, sin pedir correo personal o contraseña. Si el equipo decide backend posterior: PHP + PDO MySQL/MariaDB en cPanel o API alternativa, esquema de v3, validación, CSRF si cookies, hash password_hash, sesión segura, rate limit/moderación; nunca contraseñas planas ni credenciales reales públicas. No agregar registro real durante la noche. Jueces deben explorar sin credenciales.
6. Sin IA generativa en runtime: resúmenes ES/EN por plantillas deterministas a partir de métricas, fechas y calidad. IA futura puede explicar resultados con fuentes, no medir píxeles ni determinar causas. No API de pago ni modelo pesado.

## 3. Historias de usuario y vistas
- Inicio `/` (o rutas ya existentes): marca, contexto, CTA Explore the Observatory, acceso directo, narrativa breve con motion ya existente; no scroll obligatorio ni rebranding. Navegación Inicio / Observatorio / Observaciones / Comunidad / Biblioteca / Metodología. Rutas reales, menú móvil, estado activo, botón volver, enlaces profundos funcionan con hosting estático (hash si SPA sin rewrite).
- Observatorio: selector District Central / sectores disponibles / La Tigra si geometría fuente verificada; si no, mostrar “ventana de estudio provisional” y sectores grid. Pares del catálogo con validación, fecha inicial/final, explicar incompatibilidad. Mapa pan/zoom, bounds y leyenda, comparador de misma escala y rango de color, capa ΔdB y candidatos, calidad/no-data, métricas del contrato, fecha y fuente. Sin datos → estado vacío explícito; no zeros. Sin pareja → botón comparar desactivado y explicación. Selección de sector actualiza indicador, ficha, lista y gráficos; no inventar series. Gráfico de fechas solo si existen puntos comparables, si no mostrar dos valores/tabla. Resumen simple arriba, detalles técnicos desplegables.
- Observaciones: separar `satellite_candidate`, `citizen_demo`, `external_official` por etiquetas y filtros. Estados pendiente, en revisión, verificado/descartado (solo verificación humana real si existe; acciones demo etiquetadas). Abrir detalle de sector con coordenadas/fecha/par, fuente, área, nivel de evidencia, limitaciones, recomendación de inspección. Descargar CSV de datos reales, o archivo de ejemplo rotulado. No atribuir delitos, no emitir emergencia real; nunca enviar mensajes a autoridades en demo.
- Comunidad: foro con filtros y posts semilla claramente DEMO; comentarios, likes, encuesta y votos que actualizan recuento dentro del navegador. Formulario de reporte categoría, sector, descripción, fecha; no solicitar geolocalización precisa, teléfono ni email real; no fotos personales. Vista muestra aviso “Demo data — stored only in this browser”. Sincronización multiusuario no implementada. Validar longitud, renderizar como texto (no innerHTML con input), manejar localStorage bloqueado/lleno. Botón reset demo con confirmación local, no borrar otros datos del navegador.
- Biblioteca / Learn: fichas radar/NISAR, OPERA, lectura del semáforo, planes de contingencia educativos, noticias solo verificadas con fecha y fuente o artículos educativos atemporales. Directorio de voluntariado/enlaces oficiales, no ONG/evento inventado como real. Eventos ficticios rotulados. Modal PDF de documento permitido mismo origen, título, foco inicial, trap de foco, Escape, restaurar foco; fallback descargar/abrir nueva pestaña. No cargar PDF arbitrario externo en iframe si bloqueado; enlace oficial. No mostrar instrucciones de evacuación derivadas del radar. Referir a ICF/COPECO/Bomberos y canales oficiales verificados cuando corresponda.
- Metodología: IDs de escenas, fecha de adquisición y procesamiento, colección/madurez, polarización, CRS, resolución, máscara, validación, algoritmo/umbrales, fuentes, limitaciones y descarga. Mostrar qué se implementó y qué no. Acerca de: equipo, reto, créditos/licencias, uso de IA. Sin logos de NASA generados/modificados con IA.

## 4. UX: preservar estética existente
Mantener tipografía, paleta, motion y composición actuales; no crear una nueva marca. Mejorar navegación, estados, accesibilidad, coherencia. Priorizar contraste AA cuando posible, foco visible, botones con texto, etiquetas claras, leyendas que no dependan de color, teclado y tacto, reduced motion, modales accesibles, mobile 390px/tablet 768px/desktop 1440px. Animaciones 150–300 ms sugeridas para cambios de estado; no bloquear carga ni navegación. Mapa con panel inferior móvil; carga diferida de assets. No convertir todo en un landing de scroll. Inglés funcional para jueces y español para público local. Si no hay tiempo, usar diccionario plano ES/EN, no nueva librería i18n.

## 5. Contrato entre módulos
Usar `docs/CONTRATO_CIENTIFICO.md` como norma. Frontend no calcula métricas científicas a partir de imágenes renderizadas. Puede ordenar/filtrar agregados ya calculados. Todas las cifras provienen de `results.json`; `null` significa no calculable. Datos de prueba separados físicamente de snapshots reales. Cada par tiene identificador estable y metadata; no mostrar métricas de diferentes zonas/pares mezcladas. Un `manifest.json` con `schema_version`, `status`, `snapshot_id`, `updated_at`, `catalog_path`, `results_path`, `sectors_path`; paths relativos, `status` = `ready`, `catalog_only`, `no_data` o `error`. En ausencia de manifest, UI sin datos con instrucciones; si snapshot anterior válido, mantenerlo e indicar antigüedad.

## 6. Automatización científica (misión integrada)
Ejecutar búsqueda real CMR con `scripts/search_cmr.py` incluido; después implementar adquisición earthaccess/Harmony y procesamiento según contrato. Preparar comando `python scientific-engine/run.py --config config/region.json` que valida configuración y devuelve código de error controlado, registra etapas, no redescarga, limita volumen, crea snapshots. Añadir flags de alcance `--catalog-only`, `--dry-run`, `--local-input` y `--max-granules 2` (nombres pueden adaptarse y documentarse). Flujo: consultar catálogo → verificar pareja/huella/metadatos → bajar subconjunto → leer HVHV y calidad → alinear y comparar → candidatos y métricas → exportar → validar → publicar localmente. No inventar código de API Harmony: usar docs oficiales y verificar capacidades/variables de colección concreta. Si no se consigue credencial o archivos, completar catálogo/contratos/UI y documentar; no falsificar. Automatización diaria futura ejecutada en servidor Python separado del hosting si hace falta; actualización por publicación de escenas, no tiempo real.

Ver backlog. Reusar agentes por etapa y lotes. No correr siete agentes simultáneamente ni por cada botón. Arquitecto define mapa de archivos y contratos; dos frentes máximo: ciencia y UI; después integrar comunidad y QA. Revisar cada lote, repetir máximo dos correcciones. P0 primero. No bloquear por decisiones de diseño menores. No hacer push automático, deploy ni tocar servidores. Entrega local `dist/` (o export existente), README EN, pruebas, log, evidencia y HANDOFF. ## 8. Despliegue, entrega y criterios
GoDaddy puede ser dominio, hosting cPanel o VPS; confirmar. Estático es portable: subir archivos del build (no source, .git, .env, venv, node_modules ni HDF5) al document root correcto; configurar HTTPS, verificar rutas y enlaces, PDF, caché, acceso desde incógnito móvil. No publicar la carpeta del repo completa. Si hosting solo dominio, usar alojamiento estático autorizado y conectar DNS después por propietario. Dejar zip del dist con index.html en raíz. No mezclar con entorno de producción. Comprobar página NASA y demo independiente pública (máximo 7 slides EN o video <=30 s subtítulos EN si hablado español); enlace sin registro. Declarar IA en código/datos/documentación, referencias de recursos y licencias; imágenes/video generados con IA con indicación visible según documentación compartida. No afirmar resultados que no estén en logs/snapshot. Rúbrica: impacto, creatividad, validez, relevancia, presentación. Ensayar 1 flujo: entrar → elegir par → mapa de cambios → ficha → evidencia/acción.

## 9. Definition of Done
- Build y rutas navegan; mapa y modales funcionan en escritorio/móvil; cero fallos críticos conocidos; pruebas unitarias y Playwright ejecutadas o bloqueo explícito con comando/salida.
- Datos reales trazables a CMR/gránulos, no fixtures como medición; máscara/CRS/umbral documentados; números reproducibles. Si no hay pareja, indicar `catalog_only` o `no_data`; nunca declarar la meta científica completa.
- No secretos ni archivos grandes privados en dist/Git; fuentes y licencias anotadas; demo comunitaria marcada, sin login obligatorio. No alertas oficiales.
- Evidencia: capturas reales, logs, listado de archivos, `docs/PROGRESS.md`, `docs/HANDOFF.md`, README EN y guía de despliegue. Pendientes con dueño, estado y siguiente paso. Guardar versión estable y no desplegar sin propietario.
